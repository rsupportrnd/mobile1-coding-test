# RSUPPORT mobile1 Android developer test

알서포트 코딩 테스트 참여에 감사 드립니다.
본 테스트는 **AI 시대의 개발 협업 역량**을 검증하기 위해 설계되었습니다.
단순한 구현 능력보다 **문제 정의·판단·검증·협업 흔적**을 더 중요하게 봅니다.

- 작성된 코드와 커밋/PR 서술은 인터뷰에서 함께 리뷰됩니다.
- 과제를 끝까지 완료하지 못해도 괜찮습니다. **문제에 접근한 과정과 판단 근거**가 더 중요합니다.

## 1. AI 활용 정책

**AI 도구(ChatGPT, Claude, Copilot, Cursor 등) 사용은 전면 허용·권장합니다.**
다만 아래 원칙을 지켜주세요. 상세한 내용은 [`AI_USAGE_POLICY.md`](AI_USAGE_POLICY.md) 를 참고해주세요.

| 항목 | 원칙 |
|---|---|
| 허용 범위 | 설계 토론, 코드 생성·리팩토링, 디버깅, 문서 작성 모두 허용 |
| 기록 의무 | **사용한 주요 프롬프트/대화 맥락을 남겨주세요.** 방법은 자유 — 커밋 메시지, `AI_NOTES.md`, PR 본문 등 |
| 비밀 업로드 금지 | API 키·토큰·사내 코드를 AI에 업로드하지 마세요 |
| 검증 의무 | AI가 생성한 코드를 **그대로 제출하지 마세요.** 직접 읽고 테스트하고 의도대로 고쳐주세요 |
| 라이선스 | AI가 끌어온 외부 코드·이미지의 라이선스를 확인해주세요 |

> 면접에서는 "AI에게 무엇을 어떻게 시켰는지"와 "AI 산출물의 어떤 부분을 어떻게 고쳤는지"를 질문할 예정입니다.

## 2. 수행 가이드

- **권장 시간**: 4~8시간
- **범위 조정 자율**: 요구사항 전부를 구현할 필요는 없습니다. 선택한 scope와 제외한 이유를 PR에 기록해주세요.
- **막혔을 때**: 고민한 흔적을 남기고 진행 가능한 다음 단계로 이동하는 편이 낫습니다. 마지막에 "막힌 지점과 가설"을 PR에 써주세요.
- **해결 수단**: 언어 · 프레임워크 · 플랫폼 · 빌드 도구 선택은 **완전 자유** 입니다. 저장소에 포함된 Android/Kotlin/Compose 시드는 참고용 스타터이며, 필요 시 교체·삭제하셔도 됩니다. 선택한 스택과 이유를 PR에 기록해주세요.
- **실행 환경**: 과제 특성에 맞게 실기기 · 에뮬레이터 · 데스크톱 중 자유 선택. 동작 확인 환경을 PR에 기록해주세요.
- **품질 게이트**: 본인 스택에 맞는 lint/format/test를 돌리고, 제출 전 통과하는 상태로 만들어주세요.
- **CI**: 필수 아님. 원한다면 본인 스택에 맞게 자유롭게 구성해주세요 (가산 요소).

## 4. 과제 목록 (하나 선택)

RSUPPORT가 관심 있는 모바일 원격지원 도메인 중심으로 과제를 선정했습니다.
**원하는 주제 하나**를 골라 진행해주세요. 각 과제는 **"프로토타입 수준에서 핵심 판단을 보여주는 것"** 을 목표로 합니다.

> 과제에 등장하는 특정 API(예: `MediaProjection`, `AccessibilityService`, `LazyVerticalGrid`)는 **예시**입니다. 본인 스택의 동등 수단으로 풀어도 됩니다. 선택한 수단과 이유를 PR에 기록해주세요.

### ① 공개 이미지 3컬럼 리스트
- 공개 이미지 API(Unsplash / Pexels / Pixabay 또는 동등한 공개 API 중 택1) 기반
- **3컬럼 그리드 UI** — 본인 스택의 자연스러운 방법으로 구현
- 페이지네이션, 이미지 캐싱 전략, 오프라인 동작 각각의 **선택 근거**를 명시
- API 키는 **커밋에서 분리** (예: Android `local.properties` + `BuildConfig`, iOS `.xcconfig`, 또는 스택 관용적 방식)
- 기대 수준: 3컬럼 리스트 + 페이지네이션 + 최소 1단계 캐싱

### ② 기기 핑거프린팅
- 하드웨어 속성을 조합한 기기 식별 데이터 생성
- 플랫폼 기본 광고 ID 등 쉽게 얻을 수 있는 값 외에, **대체 식별 수단의 선택 근거**를 남겨주세요
- 결과 값은 **해시 처리**
- 개인정보 관점의 판단을 함께 기술
- 기대 수준: 식별자 생성 + 해시 처리 + 권한/개인정보 관점 근거 서술

### ③ 접근성 API 기반 원격 제어 PoC
- 접근성 서비스를 구현하여 **다른 앱의 UI 트리를 읽고** 이벤트를 주입 (예: Android `AccessibilityService`)
- 데모: 본인이 작성한 간단한 타겟 앱에서 "버튼 클릭" 정도의 자동화
- 플랫폼의 권한·보안 모델 관점에서 **왜 어떤 제약이 있는지** 를 PR에 서술
- 기대 수준: 권한 승인 흐름 + 타겟 앱에서 1개 이상의 UI 조작 데모

### ④ 장시간 세션 유지 서비스
- 60분 이상 유지되는 가상의 원격 세션을 백그라운드에서 실행 (예: Android `ForegroundService`, iOS Background Modes)
- 플랫폼의 Doze/절전/앱 스탠바이 등 **대응 전략**을 명시
- 사용자 알림/상태 전환 UI 포함
- 기대 수준: 백그라운드 세션 실행 + 상태 UI + 절전 대응 근거 서술

### ⑤ 화면 공유 전송 (화면 캡처)
- 플랫폼 화면 캡처 API로 화면을 캡처, 프레임을 **로컬 파일**로 저장하거나 로컬 네트워크로 송출
  - 예: Android `MediaProjection` + `MediaRecorder`/`ImageReader`, iOS ReplayKit, macOS `CGDisplayStream`
- 성능(프레임 드랍), 해상도 조정, 종료 흐름의 트레이드오프를 명시
- 기대 수준: 권한 요청 + 프레임 1개 이상 캡처/저장 + 해상도/FPS 트레이드오프 근거

## 5. 제출 절차

1. 이 저장소를 **Fork** 합니다.
2. Clone 후 과제 브랜치에서 작업 (`feature/<과제-키워드>` 권장).
3. 커밋을 의미 있는 단위로 쪼개서 push.
4. Fork 저장소에서 **원본 저장소로 Pull Request** 를 생성합니다.
5. PR 본문은 `.github/PULL_REQUEST_TEMPLATE.md` 양식을 채워주세요.
6. PR 링크를 담당자 메일(**recruit@rsupport.com**)로 회신합니다.

PR 본문에는 다음이 반드시 포함되어야 합니다:
- 선택한 과제와 **scope 결정 근거**
- 설계 선택과 **트레이드오프**
- 선택한 스택과 이유
- **AI 활용 내역** — 도구 / 주요 프롬프트(실패 사례 포함) / 검증 방법 / 수정 지점 / AI 미사용 판단
- 동작 영상 또는 스크린샷
- 막힌 지점·가설 (있다면)
